# mensa

Terminal database client for Postgres and MySQL, built with `@opentui/core` and `nanostores` on Bun. Released for Linux x64 and macOS arm64. The README documents every feature, key and config option.

## Commands

- `bun run dev` runs the app with watch mode.
- `bun run build` compiles a binary per target in `TARGETS`, the released `linux-x64` and `darwin-arm64`, to `dist/mensa-<os>-<arch>`, and copies `scripts/linstall.sh`, `scripts/minstall.sh` and the icon beside them. It needs `bun install --os="*" --cpu="*"`, so OpenTUI's native package for each target is installed. `buildMacApp` wraps `mensa-darwin-arm64` in `dist/Mensa.app`: the binary as `Contents/MacOS/Mensa`, `scripts/launcher.sh` as `Contents/MacOS/launcher` (the bundle's executable, since an app opened from Spotlight has no terminal: it opens the binary in Terminal or the config's `terminal`, read with `sed`, which the app ignores), `assets/icon.icns`, and `assets/Info.plist` filled with the version and a build number of major × 100 + minor × 10 + patch.
- `bun run install:linux` runs `dist/linstall.sh`, which installs the Linux x64 binary to `~/.local/bin` with a desktop entry. `bun run install:macos` runs `dist/minstall.sh`, which copies `Mensa.app` to `~/Applications`, removes the quarantine attribute, signs the binary ad hoc, swaps it in (moving the old bundle aside, and back if the move fails), registers it with Launch Services and links `~/.local/bin/mensa` to it. It checks for Apple silicon with `sysctl hw.optional.arm64`, since `uname -m` reports x86_64 under Rosetta. It runs on macOS's bash 3.2, as does the launcher.
- `bun run archive` stages each release in `RELEASES` with its install script renamed to `install.sh`: `linux-x64` as a `tar.xz` with the binary and icon, and `darwin-arm64` as a `zip` with `Mensa.app`, into `dist/Release-<platform> <version>.<ext>`. It needs `bun run build` first, and `zip`.
- `bun run format` runs Biome. Run `bunx tsc --noEmit` and `bunx biome check src/` before finishing a change. There are no tests.

## Architecture

- `src/main.ts` creates the renderer via `makeApp` and registers the keyboard shortcuts. It subscribes to `$screen` and swaps the root `App`'s child between `ConnectionsScreen` and `DatabaseScreen`, destroying the old one, so each screen starts fresh.
- `DatabaseScreen` lays out `TableSidebar | TableTabs, DataGrid, QueryView.host(), DatabaseFooter | RowViewer | RowEditor`. `RowEditor.host()` is an empty box that builds the editor from `$editor`, and `RowViewer.host()` the read only view from `$viewer`. At most one of them is set. `QueryView.host(grid)` shows the active query tab's view, or else the table `DataGrid`, and sets `GridView.current` to the shown grid.
- `lib/context.ts` exports the renderer as `ctx`, which every component imports.
- `lib/store.ts` holds all shared state as nanostores atoms: `$screen`, `$connections`, `$selectedConnection`, `$connecting`, `$connection`, `$schema`, `$tables`, `$selectedTable`, `$tabs` (tab order, as `Tab` objects of kind `table` or `query`, compared by reference), `$activeTab`, `$openTables` and `$activeTable` (computed from them, for what only cares about tables), `$querySql` (each query tab's SQL, by its id, which nothing subscribes to, so it follows every key) and `$queryResults` (each query tab's last `QueryResult`), `$tableData` (a `TableData` union of loading, loaded and error per open table), `$sorts` (the sort each open table asked for, while the loaded `TableData` has the sort its rows have), `$selectedRows` (each open table's selected row as an index into its loaded rows, cleared when new rows load), the computed `$activeTableData`, `$editor` and `$editorDirty` for the row editor, `$viewer` for the row view (a `ViewerTarget` of the tab, its rows and the row), `$dialogOpen` and `$notice` for footer messages, which `clearNotice` clears as each action starts (switching tabs, sorting, refreshing, running, saving or confirming a write), so a notice stays until the next action. `setEntry` replaces or removes one entry of a record atom, and `moveSelection` steps a selection atom through an items atom. `$connecting` holds the connection being made. Components subscribe to atoms directly and pass the unbinds to `unbindOnDestroy()` from `lib/lifetime.ts`, since screens are destroyed.
- `lib/database.ts` is the only module that touches the `Bun.SQL` client: `openClient`, `loadTable`, `forgetTable` and `closeClient`. Values are always parameters. A connection's `driver` is also its Bun adapter, and picks a `Dialect` with the identifier quote, the text cast for each column's data type and the schema whose tables are listed (`public`, or MySQL's `DATABASE()`). Loaded `TableData` keeps the column types. Names are quoted with the dialect's `quote` and passed through `sql.unsafe`, because `sql()` splits identifiers on dots. The dialect's `describe` reads the table's `TableMeta` on every load, sorts included, so the columns and keys follow schema changes, kept in the loaded `TableData` as `meta`. It gives each column a `TypeKind` for its header icon, from Postgres's type category and base type or MySQL's `data_type` and `column_type`, and the dialect's `typeKind` names one from the `information_schema` type when `describe` fails. The loaded `TableData` keeps them as `kinds`. `updateRow` saves the changed columns, matched by the primary key, with each value placed by the dialect's `param` (a cast from text on Postgres), and puts the stored row into a new rows array. `deleteRow` matches a row the same way, through `matchRow` and `matchKey`, and leaves it out of a new rows array. `truncateTable` and `dropTable` look the relation up first, so a view is dropped with `DROP VIEW`, and don't cascade. `dropTable` and `dropAll` take what they dropped out of `$tables`. `truncateAll` and `dropAll` name every table in one statement where the dialect can (the dialect's `truncate` builds the statements), without `CASCADE`, so nothing outside the schema changes, and go through the dialect's `runAll`: one transaction on Postgres, and a reserved connection with foreign key checks off on MySQL, closed if they can't be turned back on. A failed `dropAll` lists the tables again, since MySQL may have dropped some. Each table's latest load has a token in `loads`, and `loadTable` keeps its result only while its token is current: a newer load replaces it, and `discardRows`, `forgetTable` and `closeClient` remove it. `runQuery` runs a query tab's SQL on the client's `queries` pool, one connection of its own that `closeClient` closes too, so a transaction or `SET` lasts across runs and never reaches the table tabs' connections. It runs the SQL as given with `.simple().raw()`, so it may hold several statements and every value arrives as the database's text, and names the columns from Bun's `columns` (Bun 1.4.4 or later). It shows the last statement that returned columns, kept to `row_limit` rows, with a `TypeKind` per column from the dialect's `resultKinds`: Postgres reads them from `pg_type`, once per type on each connection, kept in the client's `typeKinds`, and MySQL maps the protocol's type codes. The dialect's `resultHex` names the columns of raw bytes, and any value that isn't UTF-8 is shown as hex too. Its token in `runs` works like a load's, and `forgetQuery` removes it. It resolves to a `RunOutcome`: skipped, read when every statement returned rows, ran, or wrote when a statement may have written. The user's SQL errors are shown, not logged.
- `lib/session.ts` has `connect` and `disconnect`, which open or close the client and set the store, the remembered connection and the tabs. They clear `$notice`, and changing screens doesn't. `Q` only calls `closeClient` and `flushState`, so it keeps the remembered connection and doesn't rebuild the start screen.
- `lib/tabs.ts` has `openTable`, `newQuery`, `refreshActiveTab` (reloads the active table or runs the active query), `refreshTable` (shows a table and reloads it if it was open), `showTab`, `closeTabs`, `cycleTab`, `sortTable`, `selectRow`, `setQuerySql`, `runQueryTab`, `restoreTabs` and `resetTabs`. `runQueryTab` lists the tables again after a run with a statement that returned no rows, since Postgres tags `CREATE TABLE AS` as `SELECT`, and reloads the open ones after a run that may have written. `runActiveQuery` runs the active query tab for the `Ctrl+Return` shortcut. `sortTable` cycles a column through asc, desc and none, and reloads the table with `ORDER BY`. Each saves the tabs itself, and a tab loads the first time it becomes active. Activating a tab also sets `$selectedTable`, so the sidebar follows the tabs.
- Components are classes with a static `make()` returning an OpenTUI renderable, built imperatively. `List<T>` and `DataGrid` instead extend `core.Renderable` and draw only the visible rows in `renderSelf`, so large tables stay fast. `List` takes its items and selection as atoms. `loadTable` casts every column to text, so values arrive as the database formats them. `lib/grid.ts` measures and fits a `GridSource`'s cells once, caching by the rows array: a loaded table, or a query's rows with `meta` null. It puts a `*` after the names of `NOT NULL` columns from the `meta`, kept when a name is cut. `GridView` draws them, closed off by a rule on its last row that is also the footer's top border (so `DatabaseFooter` has only a bottom border), with `┤` where its rules meet the parent's right border. It scrolls with two `RuleScrollBar` children that draw only a thumb over a rule in `theme.scrollbar` (the config's `scrollbar`, or else `fg`), at `THUMB_IDLE_ALPHA`, or `THUMB_ACTIVE_ALPHA` while its bar is hovered or dragged, or for `THUMB_TIMEOUT` after `flash()`, which `GridView.scrollTo` calls for a scroll that moves, though not from `sync()`, which only keeps the offset in range. Each draws a `fillRect` in its own `renderSelf`, after the grid has drawn the rule: the horizontal one on the bottom rule and the vertical one on the parent's right border at `right: -1`, outside the grid. Menus and dialogs on `ctx.root` draw later, so they cover it. A fill that isn't opaque keeps each cell's glyph and blends its colours, so the joins show through, while an opaque one or any drawn glyph replaces it. The char plane holds grapheme ids for anything outside ASCII, so the glyphs can't be read back from the buffer. `DatabaseFooter` has no divider, so nothing draws over the bottom rule's joins. The columns scroll until the last separator lands on that border. It exposes scroll methods through `GridView.current`, the shown tab's grid, for the shortcuts. Subclasses fill in its hooks for the message, the selection (`selectedRow`, `selectRowAt`), the shown rows as a `GridSource` (`source`), the header's marker and clicks: `DataGrid` for the active table, with its sort, selection, editing and menu, and `ResultGrid` for a query tab's read only rows. `GridView` gives them `columnName`, `clickRow` (select, or view on a double click or while the view is open) and `pickRow` (for a row menu), and `lib/rowMenu.ts` has the View and Copy row items both row menus share.
- `lib/actions.ts` has the context menus' destructive actions, `deleteRowAt`, `truncateTableNamed`, `dropTableNamed`, `truncateAllTables`, `dropAllTables` and `switchTo`, `copyToClipboard` for the row menu's copies, and `refreshSchema`, which lists the tables again with `refreshTables` and shows its error. Each write is a `confirmWrite`: `confirmDiscardIf` when it would replace the edited rows, then a `Confirmation`. They all run through `report`, which clears `$notice`, and shows the error and reloads tables only while the same connection is open. `actions.ts` also has `closeTab` and `closeAllTabs`, which ask to discard the edited row when its tab closes and then before a query tab's SQL is lost, and `tabs.ts` adds `reloadTable` and `reloadOpenTables`, and closes the tabs of tables that leave `$tables` through its own listener, which also moves the sidebar's selection. `session.ts` adds `switchConnection`.
- `lib/editor.ts` has `editRow`, `closeEditor`, `editorData`, `isSameRow`, `confirmDiscard` and `confirmDiscardIf`. The editor stays open only while its table is active with the rows array it was opened on, and the module's own `$tableData` and `$activeTable` listeners close it once anything replaces the rows. Actions that leave the row go through `confirmDiscard`, which closes the editor first, asking when it has unsaved changes. `editRow` does this itself for another row.
- `lib/viewer.ts` has `viewRow`, `closeViewer` and `viewerSource`, which gives the viewed tab's rows as a `GridSource` (a loaded table, or a query's rows with `meta` null) while its tab is active with the same rows array, and closes the view through its own listeners once they change. `viewRow` goes through `confirmDiscard`, so it closes the editor, and `editRow` clears `$viewer`, so the footers' Edit and View buttons switch between them. A double click views a row, unless the editor is open. While the view is open, the grids' clicks, right clicks and `Up`/`Down` (through `GridView.stepRow`, which only finds the row and scrolls to it) move it to another row, and `Escape` closes it. Viewing a row selects it: each `GridView` listens to `$viewer` and selects the row with `selectRowAt` when the target's rows are its `source()`'s. Only a double click names the column to scroll to, so a click on another row keeps the view's scroll. The view takes no focus and has no keys of its own, so the shortcuts keep working.
- `RowViewer` shows each value in full up to `VIEW_MAX_LENGTH`, wrapped, through `displayLines()`, which keeps newlines. JSON (a `json` column, or text holding an object or array) is pretty printed with `reformatJson` and drawn by a `CodeRenderable` with OpenTUI's JavaScript tree-sitter grammar, since there's no JSON one, highlighted in the worker and drawn plain until then. `lib/syntax.ts` has `syntaxStyles()`, from the config's `[theme.syntax]` (`string`, `number`, `constant`, with GitHub's dark or light palette by default), owned by `ctx.nativeScene`. Its fields are built once per rows array, and stepping to another row only redraws the values that differ. Their labels come from `fieldHeading` in `EditorField.ts`, shared with the editor, beside a Copy button that copies the shown value and hides while it's NULL, which `copyToClipboard`'s `onCopied` turns to Copied for a moment. `Sidebar.make()` builds the frame both sidebars share (header with the title and close button, a scroll box that never takes the focus, and a footer), and `afterLayout` in `lib/lifetime.ts` runs an action now and after the next frame.
- `lib/columnKinds.ts` has `columnKind`, which gives a key column its key from the `TableMeta` and any other its `TypeKind`, and `columnIcon`, which picks the icon and its colour. `lib/grid.ts` keeps each column's icon in the `Grid`.
- `lib/clipboard.ts` has `copyText`, which writes through OpenTUI's clipboard service made on first use (the host clipboard, or else OSC 52) and resolves to the error, and `disposeClipboard`, which `Q` awaits. `lib/export.ts` has `rowAsCsv` and `rowAsJson`, which builds the text by hand so numbers keep the database's digits and JSON values are embedded with `reformatJson`.
- `lib/clicks.ts` has `DoubleClick`, which `List` and `DataGrid` use to tell double clicks by `double_click_timeout`.
- `RowEditor` builds a field per column with `makeField` from `EditorField.ts`, picked from the column's `ColumnEdit`: `TextField` (an input, or a textarea for long, multi-line and json values), `ChoiceField` (a `List` for bools and enums) or `ReadOnlyField`. Its own `ctx.keyInput` listener takes `Escape`, `Tab`, `Ctrl+S` and `Ctrl+N` with `preventDefault`, before the focused field sees them. Blur the focused field before destroying it, since the renderer keeps pointing at a destroyed one. Inputs need a large `maxLength`, since the default of 1000 cuts values. Only the root renderable can listen for layout changes, so scroll after the renderer's `frame` event instead, through `afterLayout`.
- `Confirmation.make()` opens a modal dialog on `ctx.root` and sets `$dialogOpen`, which pauses the global shortcuts until it closes. It takes the focus while it's open and gives it back when it closes. `Return` confirms and `Escape` cancels. `C`, `Q` and the row editor's discard prompt use it.
- `Menu.make()` opens a context menu at the mouse from `MenuItem` data, built into `MenuButton`s that act on mouse up, with `"divider"` entries drawn as a `Divider` between groups. It sets `$dialogOpen` like `Confirmation`, takes the focus, and closes on `Escape` or a click outside. Choosing an item closes the menu before the item runs, so it can open a `Confirmation` or another menu. `DataGrid`, `TabBar`, `TableSidebar` and `List` (through `onMenu`) open menus on a right click. The sidebar header's menu button opens the database name's menu under it, through `IconButton`, which has no event, so it passes its own position.
- `TableTabs` is always shown once connected. It holds a `TabBar` renderable that draws tabs as wide as their labels, at least `TAB_MIN_WIDTH`, with a close icon and a `+` after the last one. When they overflow, the `+` sits at the edge and the last tab is cut there with a scissor rect. It scrolls by cells, so the first tab shown may be cut and the last one meets the `+` at the end, stepping a tab at a time for the wheel and arrows and the least needed to keep the active one in view, and maps clicks to tabs or the `+` with `hitAt()`. The rule under the tabs is drawn by `GridView`, so it can join the column separators.
- `QueryView.host()` keeps a `QueryView` per open query tab, so each keeps its cursor, undo history and scroll, shows the active one and blurs hidden ones. A view is a textarea over a `ResultGrid`, or the error of its last run in its place. The host's `ctx.keyInput` listener gives the shown view `Escape` (blur) and `Ctrl`/`Alt+Return` (run) while its textarea is focused. `E` focuses the shown one through `QueryView.focusShown()`. Each view subscribes to `$queryResults` and hands its result to its `ResultGrid`, and keeps its SQL with `setQuerySql` on every key.
- `lib/shortcuts.ts` has one `SHORTCUTS` table of keys, aliases, the `screen` they apply to and actions. A shortcut without a `screen` applies to every screen. Buttons call `SHORTCUTS.x.run()` and `shortcutLabel()`, so new actions belong in this table. Shortcuts are ignored while a dialog or the row editor is open, or an input or textarea is focused (`ctx.currentFocusedEditor`). The editor's keys live in `RowEditor`, since they apply to it rather than to a screen.
- `lib/config.ts` loads `~/.config/mensa/config.toml` with top level await. It parses `connections`, `row_limit` and `double_click_timeout`, and derives the whole theme from a few base colours.
- `lib/consts.ts` holds paths and fixed values.
- `lib/state.ts` keeps app state in `~/.local/state/mensa/state.json`, loaded with top level await: the last connection's name and each connection's open and active tabs. `connect` saves the name, `disconnect` clears it, and `main.ts` reconnects on start. Saves are debounced by `STATE_SAVE_DELAY`, and `Q` calls `flushState()` before exiting.
- `NoticeText` is the footer line shared by both screens: `$notice` in the danger colour, or else a fallback text.
- Text from the database or the config goes through `displayText()` from `lib/format.ts` before it is drawn, so control characters can't reach the terminal.
- `lib/log.ts` writes errors as JSONL, one file per day, to `~/.local/state/mensa/logs`. Use `logError` and set `$notice` for user facing failures.

## Conventions

- Explicit type annotations on variables, parameters and return types, including callbacks.
- Tabs and double quotes, as enforced by Biome. `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` are on.
- When behaviour changes, update the README and `CHANGELOG.md`. Version lives in `package.json`.
- Work happens on `dev` and is merged into `main` by PR.

## Bun

Default to using Bun instead of Node.js.

- Use `bun <file>` instead of `node <file>` or `ts-node <file>`
- Use `bun test` instead of `jest` or `vitest`
- Use `bun build <file.html|file.ts|file.css>` instead of `webpack` or `esbuild`
- Use `bun install` instead of `npm install` or `yarn install` or `pnpm install`
- Use `bun run <script>` instead of `npm run <script>` or `yarn run <script>` or `pnpm run <script>`
- Use `bunx <package> <command>` instead of `npx <package> <command>`
- Bun automatically loads .env, so don't use dotenv.

## APIs

- `Bun.serve()` supports WebSockets, HTTPS, and routes. Don't use `express`.
- `bun:sqlite` for SQLite. Don't use `better-sqlite3`.
- `Bun.redis` for Redis. Don't use `ioredis`.
- `Bun.sql` for Postgres. Don't use `pg` or `postgres.js`.
- `WebSocket` is built-in. Don't use `ws`.
- Prefer `Bun.file` over `node:fs`'s readFile/writeFile
- Bun.$`ls` instead of execa.

For more information, read the Bun API docs in `node_modules/bun-types/docs/**.mdx`.
